# Code review: Instant Translate v0.4.1

Reviewed 2 October 2026 for public source and portfolio readiness. The findings below describe v0.4.1; fixes were subsequently implemented in v0.4.2. See the resolution section at the end.

## Findings

### 1. P1 — Android 8–9 cannot start the overlay

`android/build.gradle:11` declares minSdk 26, and the README promises Android 8.0 support. `OverlayService.java:187–188` unconditionally calls the three-argument `startForeground`, introduced in API 29. Starting translation on API 26–28 can throw `NoSuchMethodError`; the surrounding `catch (Exception)` does not catch that error.

Use the two-argument overload below API 29, with a version guard around the newer overload, or explicitly raise the supported minimum. Android lint confirms this error. Verify startup on the minimum supported API as well as Android 14+.

Reference: [Android Service API](https://developer.android.com/reference/android/app/Service#startForeground(int,android.app.Notification,int)).

### 2. P1 — Changes during translation can leave the previous screen's translation displayed indefinitely

`OverlayService.java:416` returns before acquiring or comparing frames while a translation batch is busy. If the underlying page changes during OCR/translation and no relevant accessibility event arrives, no refresh is queued. Rendering the completed old batch increments `probeGeneration` at line 753, so the next probe resets its baseline to the new screen with old translations. `finishCycle` at lines 979–985 only reschedules when `pendingRefresh` is set or no translations are visible.

Example: start scanning, switch content while inference is running, then leave the new page static. With the fallback overlay or a page update that emits no handled accessibility event, old results can remain until another interaction or manual scan.

Track changes throughout in-flight work and invalidate or queue another scan when the source frame changes. Keep the source-content baseline separate from overlay redraws. Add a regression scenario where the page changes before a translation batch completes. This finding follows the control flow; it was not reproduced on a connected device during this review.

### 3. P2 — The visual refresh fallback rejects changes confined to the upper screen

`OverlayService.java:511–512` requires changes in at least 12 sampled rows and at least 22 samples in the bottom third. A changed search/header, upper product options, or partial-screen content update with an unchanged lower area cannot satisfy that condition. Accessibility handling only forwards window changes, clicks, and scrolls; an asynchronous content update can bypass those events too.

Remove the mandatory lower-screen condition or use region-based detection that distinguishes animations from changed text. Verify a static lower half with changing Chinese text above it. Preserve the requirement to keep translations stable when source text has not changed.

### 4. P2 — Rotating the composer loses the user's message and translation

`ComposeActivity.java:104` creates the input without a stable view ID. There is no saved-state handling for input, output, or the `translated` field, so activity recreation resets the composer. The asynchronous listeners at lines 171–175 also retain the old activity, while `onDestroy` at lines 236–238 closes its translator; a pending model-download callback can attempt translation after the client has been closed.

Save and restore the message and result, give editable views stable IDs, and make translation work lifecycle-aware. Test rotation while typing, downloading the model, and translating, plus process recreation.

### 5. P2 — The floating controls obscure the source being recognized

`OverlayService.java:398` hides the translation layer before capture, but the duck and its separate menu windows remain visible. They are created at lines 824 onward and 876 onward. A scan while the duck covers Chinese text, or while its menu is open, captures those controls instead of the original pixels. Text beneath them cannot be recognized in that scan.

Exclude all app-owned overlay windows from the source capture using a coordinated hide/capture/restore sequence. Verify OCR beneath the duck and beneath an open menu while keeping the controls' position and state intact.

### 6. P2 — A first public commit could include the APK signing key

There is no `.gitignore`, and `work/android-build/debug.keystore` is present. `android/build.gradle:25` uses this key to sign the distributed debug APK. Git currently tracks no files; `work/`, `outputs/`, and build directories are all untracked and eligible for a blanket `git add .`.

This is an exposure risk, not evidence that the key has already been published. Exclude keystores, local caches, generated builds, and OS metadata before the first commit. Retain the private key outside the public repository and use an appropriate release-signing setup for public releases. Anyone possessing the signing key can sign an APK with the same identity as these debug builds. The generated source ZIP already excludes the work directory.

### 7. P2 — Attribution is hidden while overlay results are shown

`OverlayService.java:897–901` places the Google attribution badge inside the optional duck menu. Normal translated overlays at lines 697–753 display results without visible attribution. Moving the credit into the menu implemented the requested visual design, but does not meet the current published requirement to show attribution adjacent to translation results.

Resolve this before distributing the portfolio build. Design a compact visible attribution area outside the source text rectangles, and confirm its placement meets the provider's guidelines. If the desired design cannot accommodate the attribution, revisit the translation provider.

References: [ML Kit translation usage guidelines](https://developers.google.com/ml-kit/language/translation/translation-terms), [Google translation attribution requirements](https://docs.cloud.google.com/translate/attribution).

## Verification

- Android lint ran against the current project and failed: **3 errors, 32 warnings**.
- One error confirms finding 1. The other two are `WrongConstant` at `OverlayService.java:739` and `:770` for break-strategy arguments. They block a clean lint gate; this review does not treat the equal-valued constants as demonstrated runtime failures.
- The existing extracted Java batch harness passed checks for immediate cached rendering, duplicate translation suppression, batch completion, and invalidation before starting work. It is an ad hoc harness, not an integrated Android regression suite.
- Prior verification built and signature-checked v0.4.1. The documented Android 14 emulator screenshot checks were performed for v0.4.0; they are not evidence of live Taobao behavior or full v0.4.1 device regression coverage.
- No connected-device reproduction was performed in this review. Findings 2–5 are based on source control flow and lifecycle handling.

## Portfolio preparation after the correctness fixes

1. Add `.gitignore` before staging files and inspect the staged file list.
2. Choose and add a license so others know what reuse is permitted. Public source without a license does not communicate permission to reuse it.
3. Make a fresh-clone build work with a documented SDK/JDK setup and standard private debug-key generation. Add a portable Gradle wrapper workflow and CI for build, lint, and meaningful regression tests.
4. Add focused tests for page changes during inference, partial-screen updates, composer recreation, and supported Android versions.
5. Separate capture scheduling, OCR/translation batching, and overlay presentation from the roughly 1,000-line service. This will make the tricky refresh behavior easier to test and explain.
6. Update the README to identify the version and environment of each verification result. Include a short demo, architecture overview, permission explanation, and clear translation/latency limitations.

Recommendation: address findings 1, 2, 6, and 7 before a public portfolio release, and resolve the remaining reliability findings before presenting the app as stable.

## Resolution: v0.4.2

- Finding 1: guarded the API 29 foreground-service overload; API 26–28 use the compatible overload. The lint error is resolved; an Android 8–9 device check is still needed.
- Findings 2–3: visual comparison runs during OCR/inference and keeps the captured source as its baseline. Changes remain dirty until a new source capture; upper-screen changes no longer require lower-screen changes. Accessibility content-change events are handled as well as clicks, scrolls, and window events. Our own overlay rectangles are masked, and moving the controls gets a short settling window.
- Finding 4: stable input ID and saved state preserve composer input, output, and pending translation source. A recreated composer restarts pending work; callbacks from a destroyed instance are ignored before using its closed translator.
- Finding 5: source capture hides and restores the translation layer, duck, and menu together. Control location and menu state are retained.
- Finding 6: `.gitignore` excludes signing files, `work`, outputs, builds, and OS metadata. Fresh source builds use the standard Android debug key; local installs retain their existing private key for update compatibility. Source archive inspection confirms no signing key or generated APK is included.
- Finding 7: the official attribution badge stays visible beneath the draggable duck, separate from translated text rectangles. Translation actions use provider attribution.
- Repository preparation: added MIT as the draft license, Windows wrapper support, checksum pinning, five integrated unit tests, and GitHub Actions for build/lint/tests. README now distinguishes prior-version verification from current checks.

### Checks performed

- Final packaging script: successful APK build, **5 tests passed**, **lint 0 errors / 34 warnings**, APK signature verification, and source ZIP integrity/contents checks.
- A clean extracted source copy built, linted, and tested without the project's signing key, using cached dependencies. This validates fresh source configuration, not a fully cold network build. Wrapper download stalled twice in this environment; packaging used the existing pinned Gradle distribution.
- v0.4.2 signing certificate matches v0.4.1, preserving update compatibility.
- Android 14 emulator: composer English message and Chinese result survived rotation; overlay translated 17 lines on a locally displayed Taobao product screenshot; duck menu and dragging worked. After the page settled, capture diagnostics stayed at four captures across the static observation interval, with no further scan.

### Remaining limits

- With Accessibility disabled, source changes completely hidden under old translation patches cannot be seen by visual comparison and may need the manual translation action. Accessibility content events improve this case without periodic hiding of unchanged text.
- Capturing a changed screen briefly hides app-owned overlays to recover original pixels. Unchanged screens are not scanned periodically when translations are present. Animated content can still trigger additional scans.
- Real Taobao, Android 8–9 runtime behavior, and rotation during a model download still need device checks. Existing OCR/translation quality and truncation limits remain.
- CI is configured but has not run on GitHub. The remaining lint warnings and further separation of the large overlay service are follow-up maintenance items.
